# 导师模型概念缺失核查报告

**日期**: 2026-08-03  
**核查人**: SelfBrain 总调度 Agent  
**触发**: 用户发现"导师模型"概念在现有 15 章技术规格中完全缺失  
**关联研究**: research/model-comparison/ 模型对比研究报告

---

## 核查结论

**"导师模型"（Mentor Model）概念在全部 15 章 docs 中完全缺失。** 现有架构只定义了外部模型作为"执行引擎"，没有区分"导师模型"作为"方法指导者"的角色。

---

## 问题定位

### 1. 缺失的概念定义

导师模型的核心设计思想：
> VibeThinker 作为大脑在面临自己无法解决的问题时，**抽象化问题（不含敏感数据）后咨询一个最强的导师模型**，获得方法论/策略指导后，由 VibeThinker 自己执行。

这是与现有"执行引擎"调用模式的根本区别：

| | 执行引擎（现有） | 导师模型（缺失） |
|---|---|---|
| 调用时机 | 数据处理阶段 | 策略决策阶段 |
| 发送内容 | 加密后的数据 | 抽象化问题描述（不含数据） |
| 期望返回 | 分析结果/代码/生成内容 | 方法论/策略/步骤建议 |
| 最终执行者 | 外部模型直接输出 | Core 拿到建议后自己执行 |
| 数据泄露风险 | 有（需加密） | 零 |

### 2. 缺失的三个层面

| 层面 | 说明 | 状态 |
|------|------|------|
| 感知层 | VibeThinker 如何知道自己"不知道" | 完全缺失 |
| 机制层 | 导师模型怎么接入、怎么调用 | 完全缺失 |
| 能力层 | VibeThinker 需要训练出"自我评估"能力 | 完全缺失 |

### 3. 现有架构的盲区

现有 02-核心架构.md 的架构图只展示了两个方向的外部模型调用：
```
Core → GPT-4 (执行引擎)
Core → Claude-3 (执行引擎)
```

没有"导师咨询"这一路径。

---

## 解决方案设计

### 双层检测机制

```
第一层：规则引擎（硬判断）
- 查询复杂度评分 > 阈值 → 触发导师
- 查询类别在白名单外 → 触发导师
- VibeThinker 输出置信度 < 阈值 → 触发导师

第二层：模型信号（软判断）
- 微调中加入"能力边界"训练数据
- VibeThinker 推理时输出置信度分数
- 输出 <uncertain> 标记触发导师
```
